# App Components Starter

A starter repository for building a small library of **framework-agnostic web
components**, in the style of the
[Government of Canada Design System (GCDS)](https://github.com/cds-snc/gcds-components):

- **[Stencil](https://stenciljs.com)** compiles components to standard custom
  elements. No React/Angular/Vue wrappers are generated — just `.js` you can
  drop into any HTML page with a `<script type="module">` tag.
- **[Eleventy](https://www.11ty.dev)** builds a documentation site: a
  homepage listing every component, and one page per component with live
  demos, a props table, events, and slots — modelled on how GCDS documents
  its components.
- **[Playwright](https://playwright.dev)** runs end-to-end tests against the
  real, compiled custom elements in an actual browser (Chromium, Firefox,
  and WebKit).

A single sample component, `<app-alert>`, is included end-to-end (component +
docs page + Playwright tests) as a template for adding more.

## Project layout

```
├── src/
│   ├── components/
│   │   └── app-alert/
│   │       ├── app-alert.tsx        # component logic/markup
│   │       ├── app-alert.css        # component styles (scoped via shadow DOM)
│   │       ├── component.meta.json  # feeds the docs homepage listing
│   │       └── readme.md            # auto-generated by `stencil build`
│   ├── index.ts                     # barrel export of all components
│   └── index.html                   # dev/test playground page
├── docs/
│   └── src/
│       ├── _includes/layout.njk     # shared page shell (nav, footer, loads the built JS)
│       ├── _data/components.js      # discovers every component.meta.json
│       ├── index.njk                # homepage: lists all components
│       └── components/app-alert.njk # per-component docs page
├── tests/
│   └── e2e/app-alert.spec.ts        # Playwright tests for app-alert
├── stencil.config.ts
├── playwright.config.ts
└── package.json
```

## Getting started

```bash
npm install

# Component development, with live reload at http://localhost:3333
npm start

# Build the component library (outputs to dist/, loader/, and www/)
npm run build

# Build & serve the documentation site (rebuilds components first)
npm run docs:serve

# Run the Playwright test suite (builds components, then serves + tests www/)
npx playwright install   # first time only, downloads browser binaries
npm test
```

## How the pieces connect

`stencil build` produces a browser-ready bundle at
`www/build/gcds-ext-mws.esm.js` (plus a legacy `nomodule` fallback). Both
the docs site and the Playwright tests load this same bundle:

- `docs/.eleventy.js` copies `www/build` into the built docs site as `/build`,
  and `docs/src/_includes/layout.njk` loads it with a `<script type="module">`
  tag — the same two lines any consumer of the library would add to their
  own page.
- `playwright.config.ts` runs `npm run build` and then serves the `www/`
  folder directly, so tests exercise the compiled custom element, not the
  TSX source.

## Adding a new component

1. `mkdir src/components/app-<name>` and add `app-<name>.tsx` (+ `.css`),
   following the pattern in `app-alert.tsx`. Stencil auto-registers any
   component with an `@Component({ tag: 'app-<name>' })` decorator — no
   manual registration step needed.
2. Export it from `src/index.ts`.
3. Add a `component.meta.json` next to it (`name`, `tag`, `description`,
   `status`, `docsPath`) — it will automatically appear on the docs
   homepage.
4. Add a documentation page at `docs/src/components/app-<name>.njk` with a
   `permalink` of `/components/app-<name>/`, matching `docsPath` above.
5. Add `tests/e2e/app-<name>.spec.ts`, and add a demo usage of the component
   to `src/index.html` so Playwright/the dev server can find it.

## Notes on conventions borrowed from GCDS

- Components are prefixed (`app-*` here; GCDS uses `gcds-*`) and use Shadow
  DOM for style encapsulation.
- Every component ships its own scoped CSS file rather than a shared
  stylesheet, so components stay drop-in portable.
- `docs-readme` Stencil output target auto-generates an API reference
  (`readme.md`) per component from JSDoc + prop/event/slot types — this is
  duplicated by hand into the Eleventy page here for a nicer, styled
  presentation, but you could just as easily have Eleventy read the
  generated readme.md files directly if you prefer less duplication.
